ConsensusProbe: Disagreement-Driven Interactive Gates
for Reliable LLM-Based Data Cleaning
Anonymous Authors
Anonymous Institution
Abstract—Large language models can produce cleaning plans for tabular data, but several plans for the same table often disagree, and a pipeline that applies one of them without comment may delete or rewrite valid records. This paper presents ConsensusGate, a policy that samples K plans, converts each into a set of cell-level edits, and asks the operator a question only when the plans differ on a destructive edit. We compare it with six baseline policies on 100 synthetic retail and inventory tasks with five types of ambiguity, using 7200 runs under three simulated operators. ConsensusGate gives a silent-error rate of 0.0\%, against 5.0\% for a single plan, and asks 0.38 questions per task where asking every time needs 1.00. Two primary pre-specified hypotheses hold (H1, H3); non-inferiority to always asking (H2) could not be confirmed; and H4 holds on the overhead criterion only and is uninformative because the sentinel never fired. A canary-based variant, ProbeGate, recorded zero probe violations across 300 candidate plans; a post-hoc code audit confirmed that mock plans never deleted the unique safe probe row, and an exploratory positive control verified 100\% sentinel triggering under forced deletion. All plans come from a seeded mock LLM, so the numbers describe the policy under simulated noise and not the behavior of a deployed model.

Index Terms—data cleaning, large language models, ensemble disagreement, human-in-the-loop, clarification questions

I. INTRODUCTION

Data cleaning is among the most time-consuming steps of analytics work. Assistants built on large language models~[brown2020,openai2023] let a user describe a cleaning job in plain language and receive executable code. Data agents such as LAMBDA~[lambda2025] and Data Interpreter~[datainterp2024] run the generated code and repair it when execution fails, and the area has grown quickly enough to be surveyed~[sunsurvey2024]. Evaluations still show that current agents do not automate complete data science workflows reliably~[cao2024], and PrepBench~[prepbench] reports that unclear instructions are a frequent cause of failure in data preparation.

Failures of this kind are hard to notice. A plan may merge categories that should stay separate, remove rows that hold valid data, or convert a column to a type that discards information, and the cleaned file still looks normal. Take two product names that differ only in letter case. Whether they are duplicates depends on what the owner of the data intends, and a model asked once will simply pick an answer. Hallucination in LLM output is a documented problem~[huang2023], and in a cleaning pipeline its effect is silent.

Asking the operator about every decision is not practical. We instead use the agreement between independently sampled plans as the signal. If K plans for one table make the same destructive edits, the task probably has an obvious solution. If they do not, a decision from the operator is needed. A similar idea has been used for code generation~[clarifygpt2024], where candidate programs are executed and a question is asked when their outputs differ. We apply it to tables and compare plans through the cell edits they produce. The experiments in this paper test the policy itself. They do not test the assumption that real LLM plans disagree exactly when a task is ambiguous, because the mock provider used here builds that behavior in.

The main contributions are the following. \begin{enumerate

  • ConsensusGate, a policy that samples K=3 cleaning plans, measures how much their edits disagree, and consults the operator only when the disagreement involves destructive edits.
  • ProbeGate, an extension that injects temporary probe rows into the dataset to monitor for unintended record deletion. In benchmark runs well-behaved plans produced zero probe violations, and an exploratory positive control confirmed the detection path triggers under forced deletion (Section~sec:probegate).
  • Track~S, a synthetic benchmark of 100 tasks with gold edits and five ambiguity types, used for 7200 evaluations of eight policies under three simulated operators. \end{enumerate

    Specifically, ConsensusProbe is the overall software framework; ConsensusGate is the core disagreement policy; ProbeGate is the canary-checking variant; and Track~S is the synthetic evaluation benchmark. The rest of the paper is organized as follows. Section~sec:related reviews related work, Section~sec:method describes the method, Section~sec:setup the experimental setup, and Sections~sec:results and~sec:ablations the results. Section~sec:limits discusses limitations, Section~sec:future the planned validation with live models, and Section~sec:conclusion concludes.

    II. RELATED WORK

    A. LLM Agents for Data Work

    General-purpose models such as GPT-4~[openai2023] are the basis of a growing set of agents for data tasks. LAMBDA~[lambda2025] couples a programmer agent, which writes code from the user's request, with an inspector agent that suggests repairs when the code fails, and the user can also step in directly. Data Interpreter~[datainterp2024] and TaskWeaver~[taskweaver2023] organize their pipelines around planning and tool use. Multi-agent frameworks such as MetaGPT~[metagpt2023] and AutoGen~[autogen2023], and code generators that test their own output~[agentcoder2023], follow a similar pattern. Overviews are given in~[sunsurvey2024] and~[guo2024]. These systems rely mainly on execution feedback, so code that raises an error gets revised. An edit that runs cleanly but removes valid rows produces no such signal, and that is the case our policy addresses. For cleaning proper, Narayan et al.~[narayan2022] showed that prompted foundation models can handle tasks such as record matching and imputation with few labeled examples.

    B. Clarification and Human Input

    ClarifyGPT~[clarifygpt2024] generates several programs for one requirement, runs them on test inputs, and poses a question when their outputs differ. It is the method closest to ours. Our setting differs in two respects. The artifact is a cleaning plan applied to a table, and plans are compared through the edits they make instead of the values they return. PrepBench~[prepbench] is a benchmark in which agents prepare data while a simulated user answers their questions. It measures agents and does not propose a rule for when to ask. The part that domain experts play in passing missing knowledge to the people who build data and language models is studied in~[park2021].

    C. Agreement Between Samples

    Sampling several outputs and keeping the most frequent answer is known as self-consistency~[selfcons2023]. Our fallback, used when the operator does not answer, is a majority vote of this kind. The value of an ensemble depends on its members being reasonably accurate and making different mistakes~[dietterich2000]. In ConsensusGate, disagreement is not used to choose an answer. It is used to decide whether a person should be asked.

    III. METHOD

    D. Operations and Edit Atoms

    A cleaning plan is a list of calls to five operations: deduplicate, normalize\_category, recalculate, handle\_missing and convert\_type. Each operation receives a read-only copy of the table and returns a new table together with a Patch object. The patch stores the deleted row identifiers, a map from (row, column) to the new cell value, and the rows flagged for manual review. We reduce a patch to a set of atoms, ("del", rid) for a deleted row and ("edit", rid, col, repr(v)) for a changed cell. Flags are not part of the set.

    E. Disagreement Score

    For each task, K plans are produced with seeds obtained by hashing the task seed, the system name and the plan index with SHA-256. Every plan runs on its own copy of the table and yields an atom set E_k. The disagreement score is the mean Jaccard distance over all pairs of plans, \begin{equation \bar{d = \frac{2{K(K-1) \sum_{i d(E_i, E_j), \qquad d(E_i, E_j) = 1 - \frac{|E_i \cap E_j|{|E_i \cup E_j|. \end{equation It equals zero when all plans make exactly the same edits and one when no two plans share an edit. With the mock provider the plans are independent because their seeds differ. A real model would have to obtain this through temperature or prompt variation, and its plans would probably be correlated (Section~sec:limits).

    F. ConsensusGate (System~E)

    The policy proceeds as follows (Fig.~fig:consensus_flow). \begin{enumerate

  • Generate K=3 plans and compute \bar{d.
  • If \bar{d > \tau_d and the disagreement involves destructive atoms, show the conflicting atoms to the operator as a question.
  • If the operator answers, rank the plans by agreement with the answer and apply the best one.
  • If the operator declines or is unsure, apply the majority vote over the K plans and flag every atom that is not unanimous. \end{enumerate The threshold \tau_d = 0.0 was chosen on 20 DEV tasks (seeds 1000--1019) by maximizing task-success F1 under leave-one-out cross-validation, which gave a DEV F1 of 0.8522 (Fig.~fig:calibration). At this value the gate asks whenever any destructive disagreement exists, so the score \bar{d acts as a yes/no test. We keep the continuous score because it is needed for calibration and because a live model may call for a nonzero threshold.

    G. ProbeGate Extension (System~F)

    System~F extends ConsensusGate with canary probe verification. Before consensus resolution, temporary canary rows are injected into a working copy of the table: two known duplicate rows and one unique calibration probe row. Each candidate plan is executed on this augmented table, and the sentinel monitors whether any plan deletes the unique calibration probe row. If any plan deletes this safe probe row, the system sets an alert flag (any\_unsafe = True), which forces human clarification by satisfying the question gate (should\_ask = consensus.should\_ask(tau\_d) or any\_unsafe).

    In the ablation benchmark (100 TEST tasks \times K=3 plans = 300 plans checked standalone in the ablation script) and across all N=900 runs in the main evaluation, exactly 0 plans deleted the unique probe row (0 probe violations out of 300 candidate plans, or 0.0\%). A post-hoc code audit revealed the reason: because the mock provider generates well-behaved deduplication plans that match on duplicate keys, and because the safe probe row is completely unique with no missing fields, no plan ever targeted it for deletion. The sentinel therefore never fired during standard benchmark runs, providing no evidence about detection ability under nominal conditions.

    To verify that the detection path functions when a true violation occurs, we conducted a post-hoc, exploratory positive-control experiment (Table~tab:positive_control). Across 300 evaluations (100 TEST tasks \times 3 trials), we injected an over-aggressive category deduplication operation into one of the K=3 plans, forcing the deletion of the safe probe row. The sentinel fired in 100.0\% of runs (300/300, 95\% CI [100.0\%, 100.0\%]), with a 0.0\% false-alarm rate on clean control (0/300, 95\% CI [0.0\%, 0.0\%]). Both System~E and System~F asked questions on 100.0\% of runs because the injected fault also elevated \bar{d above \tau_d=0.0. This confirms that the implementation's detection path triggers as designed, although detection under forced fault injection is near-guaranteed by construction.

    IV. EXPERIMENTAL SETUP

    I. Benchmark

    Track~S consists of synthetic retail and inventory CSV files with controlled quality problems. Each task is generated from a seed and has a gold label listing the required edits, the forbidden edits and an ambiguity class. The 100 TEST tasks (seeds 5000--5099) do not overlap with the 20 DEV tasks used for calibration. There are five ambiguity types (Table~tab:ambiguity, Fig.~fig:ambiguity_dist), and about half of the tasks are labeled ambiguous. This matches the precision of the always-ask policy C (49.0\%), since a policy that asks every time has a precision equal to the share of ambiguous tasks. The mock parameter p_{\text{amb=0.4 controls how much the plans vary and is a separate quantity.

    A. Simulated Operators

    Simulated users have been used in related evaluations~[prepbench,clarifygpt2024], although ours follow fixed rules and are not LLM-based. The oracle always chooses the gold option. The noisy user chooses it with probability 0.8 and a random alternative otherwise. The unsure user answers ``unsure'' with probability 0.3, which triggers the majority fallback with flagged rows, and otherwise behaves like the oracle. Each configuration is run in 3 independent trials.

    B. Metrics

    Task success is 1 when all required edits are applied and no forbidden edit is applied. Silent error is 1 when a forbidden destructive edit is applied without a question and without a flag. Questions is the number of clarification rounds per task, and precision is the share of questions that fall on ambiguous tasks. Tokens is the whitespace token count of all prompts and outputs, and latency is 1.0 plus 0.5 per question round. Silent error is zero by construction for any policy that questions or flags every destructive edit, so it should be read together with success and questions. In the mock, tokens depend only on K and latency only on the number of questions, so these two columns carry no independent information.

    C. Statistics and Reproducibility

    We use a paired bootstrap~[efron1993] with 10{,000 resamples (seed 20261105) and report 95\% percentile intervals. The p-values are adjusted with the Holm--Bonferroni method~[holm1979] over the four primary hypotheses, and the two-sided bootstrap p-value is \min(\mathbb{P(X>0), \mathbb{P(X<0)) so that mass at zero is not counted twice. The hypotheses and the frozen configuration are locked by SHA-256 digests in prereg/lock.json. The lock sits in the repository and not in an external registry, so we call the hypotheses pre-specified. All randomness is seeded through random.Random or numpy.random.default\_rng, and two runs with the same seed give a byte-identical results/metrics.json. Every experiment uses LLM\_PROVIDER=mock with p_{\text{amb=0.4 and \varepsilon=0.05, and no commercial API was called.

    VII. LIMITATIONS

    \paragraph{Mock provider All plans come from a noise model and not from a real LLM. This allows exact reproduction, but real models make correlated mistakes, and an ensemble helps only when its members err differently~[dietterich2000]. If each plan makes a given error independently with probability \varepsilon, all K plans make the same error with probability \varepsilon^{K, which is far below the per-plan rate. A low silent-error rate for any policy that questions disagreement is therefore close to guaranteed here. The experiments check that the policy and its implementation behave as specified. They do not show that disagreement between real plans signals ambiguity.

    \paragraph{Edit-level comparison Disagreement is measured on exact edits, so two plans that reach the same table through different edits, for example by deleting different members of a duplicate pair, count as disagreeing. With \tau_d=0.0 this may inflate the number of questions. For the same reason the comparison lacks a ClarifyGPT-style baseline~[clarifygpt2024] that runs each plan and compares the resulting tables. Such a baseline would show how much of the benefit comes from the ensemble and how much from comparing edits.

    \paragraph{Statistical power and unexplained failures With 100 tasks the intervals remain wide (as observed with H2), and larger multi-domain enterprise benchmarks remain an important area for future evaluation. The 25\% of tasks that fail even under the oracle remain unexplained, so differences of a few points between systems should be read with care.

    \paragraph{Data and operators Track~S is generated by procedure and may miss problems found in real tables. The simulated operators are fixed rules, while real operators tire, differ in expertise and react to the wording of a question. The value K=3 was set under the mock noise model and may not suit real LLMs.

    \paragraph{Canary probe interpretation The zero probe-violation count was clarified through a post-hoc code audit: well-behaved plans never targeted the unique calibration probe row. While our exploratory positive control demonstrated 100\% sensitivity under forced fault injection, evaluating canary detection against organic errors produced by live LLM ensembles remains open.

    VIII. PLANNED VALIDATION WITH LIVE MODELS

    None of the following has been carried out yet. \begin{enumerate

  • Add a hosted model and a local open model behind the provider interface, keeping the BUDGET\_USD guard. A pilot of 20--30 tasks at K=3 needs roughly one hundred plan-generation calls per pass.
  • Sample plans from one model at fixed temperature and from several models, and report how often all plans contain the same forbidden edit.
  • Evaluate on public cleaning datasets and on at least one real retail or inventory table.
  • Compare cleaned tables as well as edit atoms, and add the table-level baseline described above.
  • Having completed the code audit and positive control for canary probes, evaluate probe-row preservation and plan-level fault injection using live LLM ensembles.
  • Re-calibrate \tau_d on live ensembles, test a hybrid policy that adds occasional random questions, analyze the failed tasks, run a small study with human operators, and register the hypotheses with an external service before the live runs. \end{enumerate

    IX. CONCLUSION

    We presented ConsensusGate, a policy that asks an operator for a decision only when several LLM-generated cleaning plans disagree on a destructive edit. On 100 synthetic tasks it reached a silent-error rate of 0.0\% with 0.38 questions per task, compared with 1.00 for an always-ask policy, and 92.1\% of its questions fell on ambiguous tasks, against 43.1\% for the confidence policy and 52.5\% for random asking. Two primary hypotheses were supported (H1, H3); H4 was met on the overhead criterion only (and is uninformative because the sentinel never fired during the benchmark); and non-inferiority to always asking (H2) was inconclusive. A post-hoc code audit resolved the zero probe-violation count of ProbeGate, and an exploratory positive control confirmed that the sentinel triggers reliably under forced fault injection. Since the plans come from a mock with independent errors, the low silent-error rate is partly a property of the simulator. Experiments with real models, as outlined in Section~sec:future, are needed before the policy can be recommended for practical use.
