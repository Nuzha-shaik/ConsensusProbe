ConsensusProbe: Disagreement-Driven Interactive Gates
for Reliable LLM-Based Data Cleaning
Anonymous Authors
Anonymous Institution
Abstract—When several LLM-written plans for cleaning the same table disagree, which one should we trust? We argue that the system should not pick one silently. ConsensusGate generates K cleaning plans, compares the edits they would make, and asks a human operator for clarification only where the plans conflict on destructive edits. We compare ConsensusGate and six baseline policies on 100 synthetic retail and inventory cleaning tasks that cover five kinds of data ambiguity. Over 7200 evaluations under three simulated-user modes, ConsensusGate (System~E) brings the silent-error rate down to 0.0\%, compared with 5.0\% for single-plan execution, and asks 0.38 questions per task on average, where an always-ask baseline asks 1.00. We pre-registered four hypotheses and report all of them. One of them, H2 (non-inferiority to always asking), was not supported. Reproducibility and mock-honesty disclosure (Rule~R7): every experiment uses a deterministic mock LLM provider (LLM\_PROVIDER=mock, BUDGET\_USD=0) driven by a seeded noise model, and no proprietary model API was called. The results therefore describe the policy logic and the consensus mechanism under controlled noise. They are not evidence about how any commercial LLM would behave, and testing with live API calls remains to be done.

Index Terms—data cleaning, large language models, ensemble disagreement, human-in-the-loop, interactive clarification, reproducibility

I. INTRODUCTION

Cleaning a table by hand is slow work: profiling columns, removing duplicates, fixing types, filling gaps. Large language models have started to take over parts of it. They can solve several classic cleaning and integration tasks with few or no labeled examples~[narayan2022], they can drive data-analysis agents~[lambda2025], and they can generate whole cleaning workflows from a table and a stated purpose~[autodcworkflow]. Benchmarks such as PrepBench, however, show that turning a natural-language request into correct data-preparation code is still hard, and that ambiguous requests are a major source of failures~[prepbench].

The failure we care about here is a quiet one. A single generated plan can merge categories that should stay apart, drop rows that hold valid data, or coerce a column into a type that loses information, and nothing in its output tells the operator that a judgment call was made.

Many of these decisions are ambiguous in a real sense. Two careful analysts could disagree on whether product names that differ only in letter case are duplicates, or on whether a missing inventory count should become zero or the column median. If we ask a model for K independent plans and they disagree on a destructive edit, that disagreement is a cheap hint that the task contains such a judgment call. This is the working assumption of the paper, and we test it only under a mock noise model. Related ideas have been used to decide when to ask about code requirements~[clarifygpt2024] and about user intent in question answering, translation and inference~[intentsim2025]. What we do differently is compare the plans at the level of the concrete edits they would make to the table.

The paper makes three contributions. \begin{enumerate

  • ConsensusGate (System~E) is an interactive policy. It generates K=3 independent cleaning plans, computes pairwise disagreement over destructive edit atoms, and asks the operator a clarification question only when the disagreement score exceeds a calibrated threshold \tau_d.
  • ProbeGate (System~F) extends ConsensusGate by injecting synthetic canary edits into one of the plans. The point is to check whether the consensus step catches a plan that is known to be wrong, or whether it is open to systematic bias.
  • A controlled benchmark of 100 tasks with gold-standard labels, five ambiguity categories and three user-simulation modes (oracle, noisy, unsure). We evaluate it over 7200 runs with pre-registered hypotheses and a fully reproducible pipeline. \end{enumerate

    II. RELATED WORK

    \paragraph{LLMs for data cleaning and preparation. Narayan et al.~[narayan2022] cast five cleaning and integration tasks, among them entity matching, error detection and imputation, as prompting problems and found that large foundation models do well on them with few or no labeled examples. Table-GPT~[tablegpt2024] goes a step further and keeps training GPT-3.5 and ChatGPT on synthesized table tasks, which improves table understanding on tasks that include cleaning and imputation. Jellyfish~[jellyfish2024] instruction-tunes open models of 7--13B parameters for error detection, imputation, schema matching and entity matching, so that the data can stay on a single local GPU. These works improve what a model can do on a cell or a record. None of them is about deciding when a whole cleaning plan is safe to run.

    LAMBDA~[lambda2025] is a multi-agent data-analysis system in which a programmer agent writes code and an inspector agent debugs it when execution fails. AutoDCWorkflow~[autodcworkflow] takes a raw table and an analysis purpose and produces a sequence of OpenRefine operations, and it comes with a benchmark that scores the final answer, the cleaned table and the workflow. LLMClean~[llmclean2024] asks an LLM to build a context model of ontological functional dependencies for error detection, and it steadies the model with prompt ensembling and a consensus step. As far as we can tell this is the closest earlier use of an ensemble in LLM-based cleaning, but there the ensemble stabilizes one output; it does not decide when to ask someone. PrepBench~[prepbench] collects 306 tasks from the Preppin' Data challenges and evaluates interactive disambiguation, prep-code generation and code-to-workflow translation, with an LLM-based user simulator answering the agent's questions. Its authors report that ambiguity is a major source of error and that the clarification questions asked by models were often incomplete or ineffective. PrepBench evaluates agents. It does not propose a policy for when to ask, which is the part we study.

    \paragraph{Classical cleaning with a person in the loop. Cleaning systems asked people for help long before LLMs existed. Chu et al.~[chu2016] survey the area, and Abedjan et al.~[abedjan2016] compared several error-detection tools on real datasets and concluded that no single tool is sufficient. HoloClean~[holoclean2017] repairs data by probabilistic inference over constraints, external data and statistics. Raha~[raha2019] and Baran~[baran2020] detect and correct errors starting from a handful of tuples labeled by the user. ActiveClean~[activeclean2016] chooses which records to clean so that a downstream model improves with little cleaning effort. Wrangler~[wrangler2011] suggests transformations from a user's selections in an interactive interface, and CrowdER~[crowder2012] prunes obvious non-matches by machine and sends the remaining candidate pairs to crowd workers for entity resolution. These systems show that asking selectively is an old and useful idea. What changes with LLM planners is the signal that tells us when to ask.

    \paragraph{Ensembles, consistency and uncertainty. Using disagreement as a signal also has a long history. Query by committee~[qbc1992] requests a label where a committee of learners disagrees, and Dietterich~[dietterich2000] explains why ensembles of accurate but diverse members tend to beat any single member. Deep ensembles~[deepens2017] turned the idea into a practical way to estimate predictive uncertainty. For language models, self-consistency~[selfcons2023] samples several reasoning paths and keeps the most common answer, which is close to our majority-vote fallback and to baseline A2. SelfCheckGPT~[selfcheck2023] flags likely hallucinations by checking whether sampled responses agree with each other. Kuhn et al.~[semantic2023] point out that samples can differ in wording and still mean the same thing, and they cluster samples by meaning before measuring entropy. We return to this in Section~sec:threats, because our edit-level comparison has a similar blind spot. Self-reported confidence is the other common route. Kadavath et al.~[kadavath2022] found that large models can judge their own answers with reasonable calibration, while Xiong et al.~[xiong2024] found that verbalized confidence is often overconfident and that agreement across samples helps. Calibration is known to be imperfect in general~[guo2017]. This is why baseline D, which relies on self-reported confidence, is part of our comparison.

    \paragraph{Ambiguity and clarification. Ambiguity has been studied well outside data cleaning. AmbigQA~[ambigqa2020] collects open-domain questions that have several plausible answers. Aliannejadi et al.~[aliannejadi2019] build a collection of clarifying questions for ambiguous search queries and show that asking them can improve retrieval. Liu et al.~[liu2023] test whether language models recognize and resolve ambiguity, and find that they struggle. CLAM~[clam2022] prompts a model to decide whether a question is ambiguous, to ask for clarification if so, and to answer afterwards, and it is evaluated with a simulated user who holds privileged information. Zhang and Choi~[intentsim2025] split the problem into deciding when to ask, what to ask and how to use the answer, and they estimate the need to ask from the entropy over user intents seen in simulated interactions. ClarifyGPT~[clarifygpt2024] samples several programs for a requirement, runs them on generated inputs, and asks a question when their outputs differ. ClarifyGPT is the closest relative of ConsensusGate. The main differences are the domain (tables and edit patches rather than functions and return values) and the unit of comparison (edit atoms rather than program outputs).

    Our work differs from this literature in three ways. First, we compare an ensemble of executable cleaning plans at the level of the edits they make, instead of relying on a model's own confidence score. Second, the policy is interactive and selective: it spends a small number of questions in exchange for fewer silent errors. Third, we evaluate under a controlled noise model, with pre-registered hypotheses, an explicit ambiguity taxonomy and a canary-based safety check.

    III. METHOD

    A. Operations and Patches

    Every cleaning step is one of five atomic operations: deduplicate, normalize\_category, recalculate, handle\_missing and convert\_type. An operation is a pure function. It receives a read-only copy of the dataset and returns a new DataFrame together with a Patch that records what changed. A Patch has three parts: deleted\_rids (a sorted tuple of deleted row identifiers), cell\_edits (a mapping from (rid, col) to the new value) and flagged (rows that need a human to look at them). The method Patch.atoms() turns a patch into a sorted, hashable set of edit atoms, each of the form ("del", rid) or ("edit", rid, col, repr(value)). Flags are left out.

    B. Ensemble Disagreement

    Given a task, the system asks a mock LLM provider for K independent cleaning plans. Each plan gets its own seed, derived by hashing the task seed, the system identifier and the plan index with SHA-256. A plan is a sequence of operations with parameters. All K plans are executed independently, and their patch atom sets E_1, \ldots, E_K are collected. The disagreement score is the mean of the pairwise Jaccard distance over all \binom{K{2 pairs, \begin{equation d(E_i, E_j) = 1 - \frac{|E_i \cap E_j|{|E_i \cup E_j|. \end{equation It is zero when all plans agree exactly and one when no two plans share an edit atom.

    C. ConsensusGate Policy (System~E)

    ConsensusGate works in four steps. \begin{enumerate

  • Generate K=3 plans and compute the mean pairwise disagreement \bar{d.
  • If \bar{d > \tau_d, where \tau_d = 0.0 was calibrated on a held-out DEV set, show the disagreeing atoms to the operator as a clarification question.
  • If the operator answers, re-rank the plans by how well they match that answer and apply the best-aligned plan.
  • If the operator declines or is unsure, apply majority-vote consensus across the K plans and flag every non-unanimous atom for manual inspection. \end{enumerate

    The threshold \tau_d = 0.0 was chosen to maximize task-success F1 on 20 DEV tasks (seeds 1000--1019) by leave-one-out cross-validation, which gave a DEV F1 of 0.8522. In practice this means ConsensusGate asks a question whenever any destructive disagreement exists among the K plans.

    D. ProbeGate Extension (System~F)

    System~F adds a canary check on top of ConsensusGate. Before consensus is resolved, we inject synthetic canary edits, known-incorrect operations on randomly chosen rows, into one of the K plans. If the consensus step fails to filter them out, the system raises an alert and falls back to the most conservative plan, meaning the one with the fewest destructive edits. Across 300 canary-augmented evaluations, 0 unsafe plans were intercepted (interception rate 0.0\%). Under the mock noise model, a canary edit looks no different from an ordinary disagreement, so all 300 canaries passed through the consensus filter. We read this as a limitation of the mock provider and not as a verdict on the idea. A live LLM ensemble would produce different disagreement patterns, and canary detection has to be re-evaluated with real API calls.

    IV. EXPERIMENTAL SETUP

    E. Benchmark: Track~S

    We built a synthetic benchmark of retail and inventory CSV files with controlled data quality problems. Each task is parameterized by a seed and carries a gold-standard label that lists the required edits, the forbidden edits and an ambiguity classification. The 100 TEST tasks (seeds 5000--5099) are disjoint from the 20 DEV calibration tasks (seeds 1000--1019).

    G. User Simulation Modes

    Simulated users are common in this line of work~[clam2022,clarifygpt2024,prepbench], though ours are rule-based and not LLM-based. Each system--task pair is run under three modes. The Oracle always picks the gold-aligned option. The Noisy user picks the gold option with probability 0.8 and a random alternative with probability 0.2. The Unsure user answers ``unsure'' with probability 0.3, which triggers the majority fallback with flagged rows, and behaves like the oracle otherwise. Every configuration is repeated for 3 independent trials.

    H. Metrics

    \begin{itemize

  • Task Success: 1 if all gold required edits are applied and no forbidden edit is applied, 0 otherwise.
  • Silent Error: 1 if a forbidden destructive edit is applied without a clarification question or an inspection flag.
  • Questions Asked: the number of clarification rounds per task.
  • Question Precision: the fraction of questions asked on tasks that are genuinely ambiguous.
  • Tokens: the whitespace token count over all prompts and outputs.
  • Simulated Latency: a base of 1.0 unit plus 0.5 per clarification round. \end{itemize

    I. Statistical Protocol

    We use a non-parametric paired bootstrap~[efron1993,berg2012] with 10{,000 resamples (seed 20261105). We report 95\% percentile bootstrap confidence intervals and apply the Holm--Bonferroni correction~[holm1979] across the four primary hypotheses.

    \paragraph{Mock-honesty disclosure (R7). All experiments use LLM\_PROVIDER=mock and BUDGET\_USD=0. The mock provider returns deterministic plans from a seeded noise model with parameters p_{\text{amb=0.4 and \varepsilon=0.05. What we measure is policy logic under simulated randomness, not the behavior of a live LLM.

    A. Hypothesis Tests

    Table~tab:hypotheses summarizes the pre-registered tests. All p-values are Holm--Bonferroni adjusted. The effects are absolute differences in the noisy user mode.

    \begin{table*[!t] \caption{Pre-registered hypothesis test results (noisy user mode, absolute differences).

    \centering \small \begin{tabular{clccc \toprule H\# & Claim & Effect & 95\% CI & Verdict \\ \midrule H1 & E silent error < A (noisy) & -5.0\% & [-10.0\%, -1.0\%] & Supported \\ H2 & E success \geq C -\Delta & -1.0\% & [-3.7\%, 1.7\%] & Not Supported \\ H3 & E success > D, fewer Qs & 11.3\% & [6.0\%, 17.0\%] & Supported \\ H4 & F error \leq E, \leq0.25 extra Qs & 0.0\% & [0.0\%, 0.0\%] & Supported \\ \bottomrule \end{tabular \end{table*

    \paragraph{H1 (Supported). In noisy mode the silent-error rate of E differs from that of A by -5.0\% (absolute difference, E minus A; 95\% CI: [-10.0\%, -1.0\%]). The negative sign means E makes fewer silent errors. This is what we would expect if the ensemble surfaces destructive disagreements that a single plan applies without comment, although our experiments do not isolate that mechanism.

    \paragraph{H2 (Not Supported). We hypothesized that the task success of ConsensusGate would be non-inferior to the always-ask policy (C) within a margin of \Delta = 2 percentage points, while asking fewer questions. The observed difference in success was -1.0\% (95\% CI: [-3.7\%, 1.7\%]). The lower bound of the interval lies below -\Delta, so we cannot rule out that E gives up more than 2 points of success relative to C. E does ask far fewer questions (a difference of -0.62 per task), but the non-inferiority claim fails. One possible reading, which we have not tested, is that asking on every task catches some useful clarifications that the disagreement filter misses, for example on tasks where all plans agree on an action that is still wrong.

    \paragraph{H3 (Supported). In noisy mode the task success of ConsensusGate is 11.3\% higher (absolute difference) than that of the confidence-threshold policy D (95\% CI: [6.0\%, 17.0\%]), and E asks -0.13 questions per task relative to D (E minus D, so a negative value means fewer questions). Under this noise model, disagreement among plans points at ambiguous tasks more reliably than self-reported confidence does.

    \paragraph{H4 (Supported on one criterion). ProbeGate (F) matches E on silent errors and questions within the measured precision (0.0\% difference in error, 0.00 difference in questions), so the canary layer adds no measurable overhead under the mock provider. The canary interception rate, however, was 0.0\% (0 of 300 injected canaries detected), so the mock noise model gives no signal that separates canaries from ordinary disagreement. H4 is therefore supported on the overhead criterion, and the canary-detection part cannot be evaluated under mock conditions.

    VIII. THREATS TO VALIDITY

    \paragraph{Simulated LLM (R7). The biggest limitation is that every result comes from a mock LLM provider (LLM\_PROVIDER=mock, BUDGET\_USD=0). The mock generates plans from a parameterized noise model (p_{\text{amb=0.4, \varepsilon=0.05) and does not call a commercial API. This gives us full reproducibility, determinism and control, but the disagreement patterns of a real ensemble may look quite different. Real models can make correlated mistakes, which an independent noise model does not produce, and the benefit of an ensemble depends on its members being diverse~[dietterich2000]. We make no claim about ConsensusGate with any specific production model.

    \paragraph{Edit-level comparison. Disagreement is measured on exact edit atoms. Two plans that end up with the same cleaned table through differently written edits, for example by removing different members of a duplicate pair, still count as disagreeing. Kuhn et al.~[semantic2023] describe the same problem for generated text and handle it by clustering outputs by meaning. We have not tried an equivalence-aware score, and with \tau_d = 0.0 such cases may inflate the number of questions. This is also the reason for deviation M1 below.

    \paragraph{Synthetic Data. Track~S consists of procedurally generated retail and inventory tables. Real data can bring domain-specific problems that our five ambiguity categories do not cover.

    \paragraph{User Simulation. The oracle, noisy and unsure users are stylized. Real operators get tired, differ in expertise, react to how a question is phrased and work under time pressure, and none of that is modeled here.

    \paragraph{Ensemble Size. We calibrated K=3 on the DEV set under the mock noise model. With real LLMs the best K may differ, because output diversity and cost differ.

    \paragraph{H2 Failure. The failed H2 deserves a closer look. One candidate explanation is that \tau_d = 0.0 still misses useful clarification opportunities, particularly on tasks where the plans agree but the agreed action is poor. A hybrid policy that adds occasional random probing to disagreement detection could close part of that gap.

    \paragraph{Canary Detection. The canary interception rate under mock conditions was 0.0\% (0 of 300 injected canaries detected). The mock's noise model does not create plan disagreements that would let the consensus filter tell an injected canary from ordinary plan variation. Whether canary detection works is therefore still open and needs live LLM calls.

    \paragraph{Deviations and Limitations (M1, M8, M9). We record three technical refinements. (1) Calibration objective (M1): the calibration of \tau_d treats disagreement as a proxy for ambiguity and does not model semantic equivalence across subsets of plans directly. (2) Symmetric confidence intervals (M8): the evaluation metrics in H1 use symmetric two-sided bootstrap confidence intervals across both the oracle and noisy modes. (3) Boundary mass in bootstrap p-values (M9): the two-sided empirical p-value keeps positive and negative deviations apart, \min(\mathbb{P(X > 0), \mathbb{P(X < 0)), so that mass at zero is not counted twice.

    IX. REPRODUCIBILITY

    Code, data generators, seeds and the frozen configuration all live in a single monorepo, in line with common reproducibility checklists~[pineau2021]. The command make verify\_all runs the whole verification pipeline: backend tests, a security scan, a lock-file integrity check, a LaTeX-macro consistency check, a same-seed determinism check and the paper build. Determinism comes from seeded random number generators (Rule~R4). All randomness goes through random.Random(seed) or numpy.random.default\_rng(seed) with seeds derived from hashlib.sha256, and every set and dict is sorted before it is iterated into an output. Running the experiment script twice with the same seed gives byte-identical results/metrics.json.

    The configuration is frozen in configs/frozen.toml and locked by SHA-256 digests in prereg/lock.json.

    X. CONCLUSION

    We presented ConsensusGate, an interactive policy for LLM-based data cleaning that treats disagreement between plans as a sign of an ambiguous decision and asks the operator only about those. On a controlled benchmark of 100 tasks, ConsensusGate reached a silent-error rate of 0.0\% while asking 0.38 questions per task, compared with the 1.00 questions of an always-ask policy. Its question precision (92.1\%) was well above that of the confidence-threshold policy (43.1\%) and the random-ask policy (52.5\%), which suggests that, under our noise model, plan disagreement is a better trigger for questions than self-reported confidence.

    Three of the four pre-registered hypotheses were supported, one of them (H4) only on its overhead criterion. The failure of H2 is a real limitation: ConsensusGate may miss useful clarifications on tasks where the plans agree on a poor action. Hybrid policies that mix disagreement detection with occasional random probing are an obvious next step.

    All results come from a mock LLM provider and should not be read as evidence about specific commercial models. Validation with live API calls is the necessary next step.
